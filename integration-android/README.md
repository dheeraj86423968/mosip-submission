# integration-android

Android integration of MOSIP Vivid liveness/PAD for the Flutter-based
[android-registration-client](https://github.com/mosip/android-registration-client) (ARC).
Recon of the target client lives in `../docs/recon/android-registration-client.md`.

> **Status (24 Oct 2026): applied to the real ARC and builds; not yet run on a device.** The 8 patches in
> `patches/` apply with `git am` to ARC `release-1.2.x` @ `240c50d9`. In the patched app, `flutter analyze`
> adds no new issue (146 before and after, all pre-existing), ARC's own Flutter tests give the same results as
> unpatched, our 5 liveness Dart tests pass, and **`flutter build apk --debug` builds** the whole app with
> `vivid-android`, MediaPipe and TFLite in it. `vivid-android` has 28 passing JVM tests. Nothing has run on a
> phone: camera, MediaPipe, TFLite, the face-match threshold and thermal behaviour are unverified, and the
> model files are not bundled. Records: `../docs/testing/android-arc-integration.md` (ARC build) and
> `../docs/testing/android-compile.md` (module compile, D8 API check). The `RandomGenerator` blocker noted there is fixed.

## Applying it to ARC (`apply-to-arc.sh`)

```sh
mvn -q install -DskipTests                             # repo root: io.mosip.vivid jars into ~/.m2
ANDROID_HOME=<sdk> FLUTTER_ROOT=<flutter 3.10.4> \
  integration-android/apply-to-arc.sh <work-dir> patch pub analyze test apk
```

Needs about 5 GB of disk for Gradle and Flutter caches plus about 2 GB for ARC's `build/`; on a small disk set
`ARC_BUILD_DIR` to a tmpfs directory (the script symlinks `build/` there).

It clones ARC at the pinned commit, `git am`s `patches/000{1..8}`, copies `vivid-android/` to `android/vivid-android/`
and `flutter/lib/liveness/liveness_{controller,overlay,messages}.dart` (+ tests) into the app, runs `sh pigeon.sh`,
`flutter analyze`, `flutter test` and `flutter build apk --debug`. `baseline` runs the same checks on the unpatched
commit. The patches:

| Patch | Covers |
|---|---|
| 0001 | audit: `Components.LIVENESS` (REG-MOD-111), `AuditEvent.LIVENESS_*` |
| 0002 | native wiring: Gradle module + mavenLocal jars, `noCompress`, protobuf dedupe, CAMERA, `MainActivity` Pigeon registration, Dagger provider, `pigeon.sh`, policy from global params |
| 0003 | l10n: `liveness_*` keys in `app_{en,fr,ar}.arb` |
| 0004 | `lib/liveness/liveness_flow.dart`: `runLivenessGate` shared by every call site |
| 0005 | resident face capture (`BiometricCaptureScanBlockPortrait`) + binding the signed `rcapture` face to the session |
| 0006 | operator onboarding face capture (`OperatorBiometricCaptureScanBlockView`) + binding; `UserOnboardService` user-id fix |
| 0007 | operator login (`LoginPage`): liveness + match against the operator's onboarded face (`ArcEnrolledFaceProvider`) |
| 0008 | supervisor packet approval (`AuthenticateDialogBox`) and operator packet auth (`GenericProcess._authenticatePacket`) |

Login / supervisor face matching uses what ARC stores at onboarding: the raw ISO 19794-5 face record in
`user_biometric.bio_template`, decoded and embedded with the same MobileFaceNet as the live anchor, cosine
similarity >= `mosip.registration.liveness.<workflow>.faceMatch.threshold` (default 0.50, uncalibrated). Details
and the ARC user-id bug it uncovered: `../docs/testing/android-arc-integration.md`.

The manual steps below are what the patches do, kept for reference.

## Dropping it into the registration client (manual; superseded by the patches)

1. **Copy the module**: `vivid-android/` -> `android/vivid-android/`.
2. **settings.gradle** (`android/settings.gradle`):
   ```groovy
   include ':vivid-android'
   project(':vivid-android').projectDir = new File('vivid-android')
   ```
   The module needs the Flutter embedding at compile time. It declares
   `compileOnly("io.flutter:flutter_embedding_debug:1.0.0-<engine>")` and reads the engine hash from
   the `vivid.flutterEngineVersion` Gradle property, or from `flutter.sdk` in `android/local.properties`
   (`bin/internal/engine.version`), which ARC already has. The module uses `build.gradle.kts`; ARC's root `build.gradle` is Groovy, which is fine. Its
   AGP (8.3.2) / Kotlin (1.9.24) versions satisfy the module. Add `mavenLocal()` to the
   `allprojects { repositories { ... } }` block (or put the api jars in `vivid-android/libs/` and
   switch the `api(...)` lines to `api(files("libs/liveness-api-0.1.0-SNAPSHOT.jar"))`).
3. **app/build.gradle** (`android/app/build.gradle`):
   ```groovy
   dependencies {
       implementation project(':vivid-android')
   }
   ```
   ARC already sets `coreLibraryDesugaringEnabled true` and `desugar_jdk_libs:2.0.4`. The api
   jars are compiled with `--release 11` and avoid APIs missing on API 28; AGP desugars `java.util.Optional`, `java.time` and
   default interface methods for minSdk 28, so nothing else is needed. Keep ARC's `JavaVersion.VERSION_21`.
   ARC's `abiFilters` can stay as they are: the patched debug APK contains MediaPipe tasks-vision 0.10.14 and
   TFLite natives for all four ABIs, x86 included (an earlier note here said x86 was missing; it is not).
   Exclude `com.google.protobuf:protobuf-java` (pulled by biometrics-util) or the duplicate-class check fails.
4. **Publish the api jars** from the monorepo: `mvn -q -pl liveness-api,device-api,liveness-core -am install`
   (the `liveness-core` artifact is written by another workstream; see "Core contract" below).
5. **Pigeon codegen**, from the ARC root after copying `vivid-android/pigeons/liveness.dart` to `pigeon/liveness.dart`:
   ```sh
   dart run pigeon --input pigeon/liveness.dart \
     --dart_out lib/pigeon/liveness_pigeon.dart \
     --kotlin_out android/vivid-android/src/main/kotlin/io/mosip/vivid/android/bridge/gen/LivenessPigeon.kt \
     --kotlin_package io.mosip.vivid.android.bridge.gen
   ```
   Add that line to `pigeon.sh`. Pigeon puts the Dart package name into the channel names
   (`dev.flutter.pigeon.registration_client.LivenessFlutterApi.onState`), so the committed outputs only
   match a package named `registration_client`. Regenerate them if the package has another name. The Kotlin sources reference the generated names
   `LivenessHostApi`, `LivenessFlutterApi`, `SessionStateDto`, `LivenessResultDto`, `ChallengeOutcomeDto`.
6. **Register the host API** in `MainActivity.configureFlutterEngine`:
   ```java
   livenessPigeonApi.attach(this, flutterEngine.getRenderer(), flutterEngine.getDartExecutor().getBinaryMessenger());
   LivenessHostApi.Companion.setUp(flutterEngine.getDartExecutor().getBinaryMessenger(), livenessPigeonApi);
   ```
   and provide it from `HostApiModule`:
   ```java
   @Provides @Singleton
   LivenessPigeonApi getLivenessPigeonApi(AuditManagerService audit) {
       return new LivenessPigeonApi(appContext,
           (ctx, governor) -> new MediaPipeLivenessEngine(ctx, ModelAssets.Companion.load(ctx, null), governor, true),
           () -> NetworkUtils.isNetworkConnected(appContext),
           (event, sessionId, detail) -> { audit.auditWithArguments(AuditEvent.valueOf(event), "REG-MOD-111", "Liveness", sessionId, detail); return kotlin.Unit.INSTANCE; });
   }
   ```
   (add the `LIVENESS_*` events to `AuditEvent` and `LIVENESS("REG-MOD-111","Liveness")` to `Components` first).
7. **Assets**: place `face_landmarker.task` (MediaPipe, ~3.6 MB), the int8 MiniFASNet-V2 80x80
   `.tflite` (~0.6 MB) and MobileFaceNet `.tflite` (~4 MB fp16) in
   `vivid-android/src/main/assets/vivid/models/` and fill their SHA-256 into `manifest.json`
   (`sha256sum file`). Placeholder digests log a warning and skip verification; never ship that.
   Signed over-the-air bundles land in `<filesDir>/vivid/models/current/` with the same layout and
   take precedence (`ModelAssets.load`).
8. **Flutter**: copy `flutter/lib/liveness/` to `lib/liveness/`, merge the ARB keys into
   `assets/l10n/app_*.arb`, run `flutter gen-l10n`, then follow `flutter/lib/liveness/integration_points.md`.

## Core contract (assumed, pending liveness-core)

`bridge/CoreBindings.kt` is the only file that imports `io.mosip.vivid.core`. It assumes:

```kotlin
LivenessSessionFactory(engine: LivenessEngine).open(policy: LivenessPolicy, ctx: SessionContext): LivenessSession
FrameSourceBridge(source: FaceFrameSource, session: LivenessSession).start(options: StreamOptions) / .stop()
```

If the core lands with different names or shapes, change that one file. Everything else codes
against the frozen `liveness-api` / `device-api` types only.

## Performance budget (PLAN 8.3)

| Metric | Target (2 GB RAM, 4x A53-class) | Where it is enforced / measured |
|---|---|---|
| End-to-end per frame, 480p, CPU | <= 80 ms | `FrameSkipper.emaProcessingMillis()`; FaceLandmarker CPU ~30-45 ms, MiniFASNet int8 ~8 ms, moiré/colour/rPPG ~5 ms, embedding (every 3rd frame) ~25 ms |
| Per frame with GPU delegate | <= 35 ms | `MediaPipeLivenessEngine(preferGpu = true)` + `TfliteTextureSignal` GPU delegate with CPU fallback |
| Model cold start | <= 1.5 s | Lazy `engineFactory` in `LivenessPigeonApi.startSession`; mmap'd models (`noCompress`) |
| APK growth | <= 25 MB | tasks-vision (~10 MB/ABI) + tflite (~3 MB/ABI) + models (~8 MB): needs ABI splits or arm64-only release |
| Throttling | 10 fps, rPPG off | `ThermalGovernor` (LIGHT/MODERATE -> REDUCED, SEVERE+ -> MINIMAL 6 fps) |
| Frame skipping under load | adaptive | `FrameSkipper` cadence stretched to the EMA of engine time |
| Quantisation | int8 texture CNN, fp16 embedding | `ModelAssets` keys `minifasnet_int8`, `mobilefacenet` |

## Unverified: check these first on a device

ARC-level items (from the patched build; see `../docs/testing/android-arc-integration.md`): the CameraX preview into
the Flutter texture inside ARC's `MainActivity`, decoding real SBI ISO 19794-5 faces (`IsoFaceImages`), the
face-match / capture-binding threshold (0.50 cosine similarity, uncalibrated, tablet camera vs SBI camera), the
`LIVENESS_CAPTURE_MISMATCH` path through `invokeDiscoverSbi`, and bundling the three model files (`VIVID_MODELS_DIR`).

Items 1, 2 and 12 below were resolved by the compile pass (see `../docs/testing/android-compile.md`):
the module compiles, the Pigeon 10.1.6 shapes are confirmed (the FlutterApi void callback is `() -> Unit`,
not `Result`), and the Dart code passes analysis. The MediaPipe and CameraX signatures in item 3 resolve
at compile time; their runtime semantics are still unverified.

1. `./gradlew :vivid-android:compileDebugKotlin` -- expect import/typo fixes; nothing here has been compiled.
2. Pigeon 10.x Kotlin output: confirm the generated method shapes (`callback: (Result<T>) -> Unit`
   for `@async`, `LivenessHostApi.setUp`, `LivenessFlutterApi.onState(.., callback)`), and that
   `Map<String?, double?>` / `List<double?>?` generate as used in `SessionDtoMapper`.
3. MediaPipe API: `ByteBufferImageBuilder(buffer, w, h, MPImage.IMAGE_FORMAT_RGBA)`,
   `FaceLandmarkerResult.faceBlendshapes()` / `facialTransformationMatrixes()` returning
   `Optional<List<...>>`, and the matrix being column-major `FloatArray(16)`.
4. Yaw/pitch sign conventions in `MediaPipeLivenessEngine.eulerFromMatrix` with the front camera
   (frames are unmirrored; `+yaw` must mean "subject turned to their own left").
5. `YuvToNv21` on real HALs (interleaved vs planar chroma, odd row strides) and rotation for
   `rotationDegrees` 90/270 on tablets in landscape.
6. TFLite tensor types of the exported MiniFASNet (uint8 vs int8 input, softmax present or not)
   and MobileFaceNet output dimension (128 vs 512).
7. `CameraState` observation via `cameraInfo.cameraState.observe(lifecycleOwner, ...)` from a
   non-main thread is not allowed; `bind()` runs on the main handler, verify no leaks on rebind.
8. The Flutter `Texture` preview path (`FlutterPreviewSurface`): `TextureRegistry` from
   `flutterEngine.getRenderer()` and `SurfaceRequest.provideSurface` executor.
9. D8 memory: ARC notes OOM at `-Xmx1536M`; raise `org.gradle.jvmargs` when adding MediaPipe.
10. `ThermalGovernor.pollHeadroom()` is called from the camera thread each frame; it should be
    rate-limited to ~1 Hz once measured.
11. All thresholds in the signals (moiré ratio 6, colour logistic, parallax 1.2 % residual, rPPG
    2 dB) are hand-set to mirror the desktop engine design, not calibrated on-device.
12. Dart side: `dart analyze` on the overlay (Dart 3 switch expressions are used; ARC pins Flutter
    3.10.4 / Dart 3.0 which supports them), and `flutter gen-l10n` with the merged ARBs.
